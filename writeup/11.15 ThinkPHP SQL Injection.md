ThinkPHP 5.0.9 SQL 注入漏洞实战 Writeup

一、 靶机信息与漏洞简介

· 靶机环境：ThinkPHP 5.0.9 (Vulhub 环境)
· 漏洞类型：SQL 注入 + 信息泄露
· 漏洞原理：ThinkPHP 5.0.9 在处理控制器方法时，如果传入的 ids 参数是数组形式，底层在拼接 SQL 语句时未做严格过滤（直接拼接了数组的键名），导致恶意 Payload 被当作 SQL 语句执行，触发 updatexml 等函数报错注入。

二、 渗透过程详解

1. 漏洞探测与报错注入

访问靶机地址，首先验证环境是否正常。构造请求：/index.php?ids[]=1&ids[]=2，页面成功回显 Hello, admin 和 Hello, test，确认环境存在注入点。

由于页面存在回显，且靶机开启了 Debug 模式，直接使用 updatexml 进行报错注入。
构造 Payload 获取当前数据库用户名：

http/index.php?ids[]=1&ids[0,updatexml(0,concat(0x7e,user()),0)]=1


页面直接抛出 PDOException，回显 XPATH syntax error: '~root@10.42.1.77'，确认注入成功且为 root 权限。

2. 获取数据与踩坑记录

接着爆出数据库名，回显为 ~cat~。结合报错页面的 Call Stack 发现底层 SQL 为 SELECT * FROM 'user'...，确认存在 user 表。

踩坑点：
尝试查询 user 表中的 flag 字段时，提示 Unknown column 'flag'。
由于想查 information_schema 的表名和列名，在浏览器地址栏输入了超长 Payload。结果遭遇了浏览器的自动 URL 编码截断，随后改用 Burp Suite 抓包重放。但在 Repeater 中连续发包时，可能触发了靶机的某种保护（或超时机制），服务器一直返回 408 Request Timeout，注入受阻。

3. 另辟蹊径：Debug 页面信息泄露

既然 SQL 注入这条路有些卡壳，决定重新审视报错页面。ThinkPHP 的 Debug 页面不仅会报错，还会暴露大量底层敏感信息。

下拉报错页面的最底部，在 Exception Data 中的 Environment Variables（环境变量）面板里，发现出题人直接把 Flag 放在了系统环境变量中：

text
FLAG   CTF2{1754e216-3a58-420e-98ea-1e8279f067e0}

提交该 Flag，成功拿分。

三、 总结

这题虽然标为 SQL 注入，但本质上是 “SQL 注入点探路 + 异常页面信息泄露” 的组合拳。出题人故意将 Flag 放在环境变量中，考验的是选手在遇到注入受阻时，能否敏锐地观察到报错页面底部的其他信息。这也提醒我们在实战中：不要死磕一条路，报错堆栈和环境变量往往是意外惊喜的来源。
